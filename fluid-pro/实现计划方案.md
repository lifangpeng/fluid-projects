# 流体网络求解与 Agent Skill 项目实现计划

## 1. 目标与交付边界

本项目交付一个可在 Linux/Docker 中运行的最小完整闭环：使用 TOML 描述流体网络及有限工况，Python 求解器计算压力、流量和流速，分析器判断流路连通性与功能可靠性，静态网页交互展示结果，并将这些能力封装成可被 Agent 调用的 Skill。

题目文档中的要求作为产品需求输入；本计划补充实现顺序、接口、验证标准和工程取舍。第一版聚焦稳态、不可压缩、单一流体、准一维管路和确定性计算，不扩展瞬态、可压缩、多相流或 CFD。

## 3. TOML 数据模型设计

### 3.1 顶层结构

采用显式、可扩展的分组，所有 ID 在文件内唯一；单位统一写入 `units`，内部计算统一为 SI 单位。

```toml
[meta]
name = "demo-hydraulic-network"
version = "1.0"

[fluid]
density_kg_m3 = 1000.0

[units]
pressure = "Pa"
flow = "m3/s"
length = "m"

[[nodes]]
id = "source"
type = "source"
pressure_pa = 500000.0

[[nodes]]
id = "tank"
type = "junction"
pressure_pa = 0.0

[[nodes]]
id = "consumer_a"
type = "load"
min_flow_m3s = 0.001
min_pressure_pa = 100000.0
function = "cooling"

[[edges]]
id = "pipe_a"
from = "source"
to = "consumer_a"
resistance = 2.0e11
model = "quadratic"
diameter_m = 0.02
length_m = 4.0
enabled = true

[[scenarios]]
id = "normal"
description = "正常工况"
set = { valve_main = "open", pump_1 = "on" }

[[controls]]
id = "valve_main"
kind = "valve"
target_ids = ["pipe_a"]
states = ["open", "closed"]
default = "open"
```

### 3.2 状态与组合控制

`controls` 定义可切换对象及合法状态，`scenarios` 只列出需要分析的有限组合；不对所有控制状态做笛卡尔积遍历。场景可通过 `extends` 继承基础场景，并用 `set` 覆盖状态。故障以 `faults` 或场景中的状态值表达，例如 `pipe_a = "blocked"`、`pump_1 = "failed"`。加载器应拒绝未知 ID、非法状态、重复 ID 和悬空边。

### 3.3 Schema 校验

第一阶段用 Python 手写结构校验和清晰错误路径（如 `edges[2].from`）；稳定后可补充 JSON Schema 导出，供 Agent 生成 TOML 时使用。校验结果分为 error（无法求解）和 warning（参数缺省、单位未声明等）。

## 4. Python 领域模型与模块接口

使用 `dataclasses` 表达 `NetworkModel`、`Node`、`Edge`、`Control`、`Scenario`、`LoadRequirement`；使用 `Enum` 表达节点类型、阻力模型和控制状态。所有输入对象保持不可变或在求解前复制，避免不同场景相互污染。

建议公共接口：

```python
network = load_network("examples/demo_network.toml")
state = network.resolve_scenario("normal")
solution = solve(network, state)
report = analyze(network, state, solution)
export_result(solution, report, "web/data/normal.json")
```

CLI 提供：`validate FILE`、`solve FILE --scenario ID --json OUT`、`analyze FILE --scenario ID`、`export FILE --all-scenarios OUT_DIR`、`serve`。

## 5. 求解算法实施方案

### 5.1 图与边界条件

将网络表示为有向图；源节点提供定压边界，已知压力节点作为 Dirichlet 边界，普通 junction 满足质量守恒，负载按指定压力/流量约束处理。每条有效边的流量正方向为 `from -> to`，结果允许为负值并在输出中标注实际方向。

### 5.2 线性模型

对 `ΔP = RQ`，按节点质量守恒组装稀疏线性方程 `A·P=b`，解出未知节点压力，再由边压差计算流量。矩阵奇异时报告孤立节点、无压力边界或闭合网络原因。

### 5.3 二次模型

对 `ΔP = R·Q·|Q|`，采用阻力导数的 Newton-Raphson 或阻尼迭代：以线性模型结果或边界压力插值初始化；每轮更新边导纳、组装压力方程，直到压力残差和流量变化均小于阈值。设置最大迭代次数、阻尼因子和非收敛诊断。低压差时对导数加 epsilon，避免数值不稳定。

### 5.4 流速、守恒与异常

若管径存在，按 `v = Q / (πd²/4)` 计算流速；缺少直径则输出 `null` 并给 warning。求解后统一校验：节点质量残差、源端总流量、压力范围、负流量、零/负阻力、未连接节点。结果应携带 `converged`、`iterations`、`residual`、`warnings`，使前端和 Agent 能解释失败原因。

## 6. 流路分析器

对每个显式场景执行以下流程：

1. 合并默认控制状态、继承场景和当前场景覆盖值。
2. 应用阀门/泵/管路故障，生成有效子图；关闭边不参与求解。
3. 从源节点执行 BFS/DFS，识别可达负载及从源到负载的候选路径。
4. 调用求解器，按负载的最小流量和最小压力阈值判定 `functional`。
5. 汇总每项功能的 `reachable`、`meets_threshold`、`reliability` 和阻断原因。

可靠性先采用可解释的离散定义：`functional = reachable and meets_threshold`；场景级可靠性为正常工作的功能数/功能总数，并同时输出关键路径、失效边和瓶颈边。后续可扩展串联系统乘积概率，但不在首版引入未经给定的故障概率。

## 7. 输出 JSON 契约

统一输出 `scenario`、`nodes`、`edges`、`functions`、`diagnostics` 五部分。节点包含压力；边包含流量、流速、压降、实际方向和启用状态；功能包含阈值比较结果。固定字段名和单位，提供 `result.schema.json`，前端只依赖该契约，不直接读取 Python 内部对象。

## 8. 可视化页面

采用无构建依赖的 HTML/CSS/JavaScript，默认使用 SVG 绘图；网络规模扩大后再引入 D3。页面加载预导出的 `data/index.json` 和场景 JSON，左侧场景/控制选择，中央拓扑图，右侧显示节点压力、边流量/流速、功能可靠性和诊断信息。边颜色表示流向，宽度表示流量，关闭/故障边使用虚线或灰色；切换场景时直接读取对应 JSON，实现静态部署下的实时切换。

若需要网页即时计算，提供可选 `/api/solve` 服务，但演示主路径必须依赖预计算 JSON，确保纯静态文件也能运行。页面应在无数据、非收敛和未知场景时显示可读错误。

## 9. Agent Skill 封装

`skill/SKILL.md` 描述触发条件、输入收集顺序、TOML Schema、CLI 命令、输出格式和错误处理。定义四类能力：

- 设计：根据自然语言生成并校验 TOML；缺失边界条件时提出最少必要问题。
- 求解：选择场景运行 `solve`，解释压力/流量和收敛诊断。
- 分析：运行 `analyze`，输出功能状态、关键路径、故障影响。
- 可视化：导出 JSON 并更新静态页面数据。

附带几个高质量示例 prompt、失败案例和安全边界（不得把未给出的物性/阈值当作事实）。本地通过模拟 Agent 调用验证后，再按 Clawhub 的清单、版本和发布命令发布，并在 README 记录版本号和链接。

## 10. Docker 与 Linux 演示

使用多阶段或精简 Python 镜像：安装锁定依赖、复制 `src` 和 `web`、以非 root 用户运行。默认命令启动静态 Web 服务（例如 `python -m http.server 8080 --directory web`）；另提供 `docker compose up --build`，将示例数据挂载为只读卷。容器内执行完整验证：解析、求解、分析、导出、HTTP 访问和健康检查。`demo-runbook.md` 写明 Linux 命令、预期输出、端口映射、常见故障排查。

## 11. 测试与验收标准

测试分层如下：

- 单元测试：TOML 校验、场景合并、状态应用、图连通性、线性/二次边模型、流速计算。
- 物理不变量：节点流量守恒、压差方向与流量方向一致、串联管路流量相等、关闭阀门流量为零。
- 场景测试：正常、单阀关闭、泵故障、负载不可达、多个独立支路。
- 回归基准：提交 `expected_demo_result.json`，固定容差比较压力、流量和功能判定。
- 端到端：CLI 导出 JSON、浏览器加载静态页面、Docker 构建/启动/健康检查。

验收以“一个命令从 TOML 得到 JSON 和报告、网页能切换至少三个场景、容器在 Linux 可复现、基准结果通过”为准。数值比较使用绝对/相对容差，并把迭代诊断纳入断言。

## 12. 分阶段排期与优先级

### P0：骨架与基准（0.5 天）

建立仓库、依赖、示例网络、CLI 骨架和 README；先写一个可手算验证的串联/分支基准。

### P1：模型、解析和线性求解（1 天）

完成 dataclass、TOML 校验、场景状态、图构建、线性方程和结果 JSON；通过单元测试。

### P2：二次阻力与分析器（1 天）

加入迭代求解、收敛诊断、路径分析、阈值判定和故障场景；锁定基准输出。

### P3：可视化（0.5 天）

实现 SVG 网络图、场景切换、指标面板、错误提示；接入导出 JSON。

### P4：Skill 与 Docker（0.5 天）

完成 `SKILL.md`、Agent 示例、Dockerfile/Compose、Linux 演示脚本和健康检查。

### P5：发布前检查（0.5 天）

运行全量测试和容器验收，补充架构/算法文档，提交 GitHub，按 Clawhub 流程发布 Skill，记录两个链接。

若时间不足，优先保证 P0–P2、静态页面和 Docker；把概率可靠性、在线 API、多种阻力公式和复杂 UI 列为后续迭代。

## 13. 风险与应对

数值不收敛时保留最后一次迭代结果并给出可操作诊断；网络缺少压力参考时在校验阶段阻止求解；状态组合膨胀时坚持只运行显式场景；浏览器直接打开本地 JSON 受跨域限制时通过静态服务器提供页面；Clawhub 发布规范变化时以其当前 CLI/网页校验结果为准，并把发布步骤写成可重复脚本。

## 14. 最终交付清单
